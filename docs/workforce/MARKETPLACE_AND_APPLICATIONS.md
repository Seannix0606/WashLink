# Marketplace and job applications (W5)

Scope: what `supabase/migrations/2026_10_25_w5a..w5e_*.sql` enforce for the worker marketplace
and job applications (spec C, B, A, D notice, I). Proven on the local Docker stack only (pgTAP
J4, J5, J17, J18 and `scripts/supabase-test/w5-api-smoke.mjs`; `LOCAL_TEST_HARNESS.md`). It says
nothing about the production project until D-10 rows 24-26 (`ROLE_AND_PROFILE_SECURITY.md`) are
answered. Legal questions are recorded in `LEGAL_REVIEW_REGISTER.md` (all OPEN); nothing here is
a compliance claim. The W5 plan names this document `JOB_APPLICATIONS.md`; it was created under
this name on request.

## Principles (continue P1-P18)

| | Principle |
|---|---|
| P19 | Every write to `job_applications` goes through definer RPCs. No client role (anon, authenticated, service_role) has INSERT / UPDATE / DELETE; the write policies are deny-all. The BEFORE guard accepts a change only under the transaction-local flag `washlink.job_application_write` = row id, or `opening:<job_opening_id>` with new status `closed` (auto-close). Trusted SQL sessions bypass the guard for repair (audited `trusted_session`), except P20. |
| P20 | `opening_snapshot` and `opening_snapshot_taken_at` are write-once: null -> value once (at submit), never changed or cleared afterwards by ANY session, trusted and service_role included (42501 `The application snapshot cannot be changed.`). Removal only by deleting the row. |
| P21 | Owners see applicant data only through `applicant_profiles_for_job_opening`; no `worker_profiles` policy is widened, and `worker_private_contacts` is never readable by owners (D-13, D-14). |
| P22 | Qualifications shown to owners come only from `applicant_verified_certifications` (workflow records, W7; zero rows in W5). The table has no column where a worker can claim a certification. Profile skills / experience are self-reported. |
| P23 | Audit payloads and notification texts never contain the cover note, the snapshot, pay, terms, the applicant's name or contact data. |

## Table `public.job_applications`

| Column | Rule |
|---|---|
| `id` | uuid PK, generated by the RPC |
| `job_opening_id` | FK `job_openings`, on delete cascade; immutable |
| `worker_id` | FK `worker_profiles(profile_id)`, on delete cascade; `auth.uid()` at create; immutable |
| `shop_id`, `owner_id` | FK `shops` / `profiles`, on delete cascade; copied from the opening at create; immutable |
| `status` | CHECK `draft, submitted, under_review, shortlisted, accepted, rejected, withdrawn, closed`; default draft |
| `cover_note` | optional, trimmed, empty -> null, <= 1000 chars; editable only while draft |
| `notice_version` | CHECK `w5_v1` (the acknowledged training and work notice) |
| `notice_acknowledged_at`, `submitted_at`, `decided_at`, `withdrawn_at`, `closed_at`, `status_changed_at` | server stamps |
| `opening_snapshot`, `opening_snapshot_taken_at` | jsonb object <= 64 KB; P20 |
| `created_at`, `updated_at` | server stamps (`updated_at` also on trusted repairs) |

`ja_submission_consistency`: submitted_at, snapshot, snapshot time, notice version and notice
time are all null or all set; draft has no submitted_at; submitted / under_review / shortlisted /
accepted / rejected have it; accepted / rejected have decided_at; withdrawn has withdrawn_at;
closed has closed_at. Unique partial index `job_applications_one_live_per_worker_opening
(job_opening_id, worker_id) where status <> 'withdrawn'`.

Snapshot (`job_opening_application_snapshot`, internal): `snapshot_version` 1,
`job_opening_updated_at`, `shop_name`, `shop_address` at that moment, and verbatim every W4
content column under its column name (title, description, duties, work_location,
openings_count, job_type, required_skills, minimum_years_experience, experience_requirement,
availability_requirement, schedule_details, compensation_*, benefits, other_terms,
minimum / preferred qualifications, required_training, applicant_requirement,
certification_expectations, application_deadline, application_instructions): 29 keys.

## State machine (`transition_job_application`)

| From | To | Who | Condition / stamps |
|---|---|---|---|
| (none) | draft or submitted | worker (self) | `create_job_application`, every apply check |
| draft | submitted | worker (self) | every apply check again + current notice version; snapshot taken |
| draft, or closed with submitted_at null (closed draft) | (deleted) | worker (self) | `delete_job_application_draft` |
| submitted | under_review | owning owner | opening published or paused |
| submitted, under_review, shortlisted | rejected | owning owner | same; decided_at |
| under_review | shortlisted | owning owner | same |
| under_review, shortlisted | accepted | owning owner | same + `is_verified_shop_owner(shop_id)`; decided_at |
| submitted, under_review, shortlisted, accepted | withdrawn | worker (self) | any opening status; withdrawn_at |
| draft, submitted, under_review, shortlisted | closed | system only | opening -> closed / archived; closed_at; a draft stays never-sent (submitted_at null, see below) |

Everything else is rejected for every end user, super_admin included (42501 `This application
status change is not allowed.`): same status, backwards, out of rejected / withdrawn / closed,
owners withdrawing, workers deciding, anyone setting closed. A caller who is not the row's
worker (role worker) or owner (role owner AND current `shops.owner_id` of the opening's shop),
or an owner on a never-sent row (submitted_at null: draft or closed draft), gets 42501 `Job
application not found.` A `p_from_status` that differs from the row gets 55000 `This application changed.
Refresh and try again.` Owner transitions when the opening is closed / archived get 23514 `This
job opening is closed.` `accepted` is an owner pipeline decision only: never a contract, an
offer of employment or a guarantee (W9 creates contracts).

## Apply refusals (create and draft -> submitted, in this order)

| Check | Error |
|---|---|
| not signed in, or role not worker | 42501 `Only worker accounts can apply to job openings.` |
| no worker profile | 23514 `Create your worker profile before applying.` |
| opening missing or draft | 42501 `Job opening not found.` |
| opening paused | 23514 `This job opening is paused and is not accepting applications.` |
| opening closed / archived | 23514 `This job opening is closed.` |
| shop fails P15 | 23514 `This shop cannot receive applications until its verification is reviewed.` |
| deadline before today (Asia/Manila; the deadline day itself is accepted) | 23514 `The application deadline for this opening has passed.` |
| W7 (D-20): opening is `certification_required` and the worker holds no CURRENT (effective active) shop-issued certification from any shop | 23514 `This opening needs a current shop-issued certification recorded on WashLink.` |
| 3 rows for (opening, worker), withdrawn included | 23514 `You cannot apply to this job opening again.` |
| 50 live (submitted, under_review, shortlisted) for the worker (also refuses new drafts) | 23514 `You have reached the limit of 50 open applications.` |
| 500 sent (submitted_at set), non-withdrawn rows on the opening | 23514 `This job opening is not accepting more applications.` |
| submitting without `p_notice_version = 'w5_v1'` | 23514 `Review the training and work notice before applying.` |
| cover note over 1000 chars | 23514 `The cover note must be 1000 characters or fewer.` |
| a non-withdrawn row already exists (also a second draft) | 23505 `You have already applied to this job opening.` |

The opening row is locked `for share` (serialises with `transition_job_opening`'s `for update`),
then the worker with a transaction advisory lock (`job_applications:<worker_id>`), then the opening
with a second transaction advisory lock (`job_opening_apps:<opening_id>`) around the 500 cap
(fix cycle 1: concurrent applicants cannot both pass the cap). The order is always opening row ->
worker -> opening advisory and nothing else takes these locks, so applies cannot deadlock.
Global order (re-review fix): job_openings row -> job_applications row -> advisory locks.
`transition_job_application` reads the row's `job_opening_id` unlocked (immutable), locks the
opening FOR SHARE, then the application FOR UPDATE, and only then checks actor, status
(staleness) and the pair; `transition_job_opening` + auto-close take the opening FOR UPDATE and
then the applications, so the two cannot deadlock. Draft edit / delete lock only the
application. Verified structurally and by behaviour tests (`j5_w5_fix1_owner_notifications_and_lock_order`),
not with two concurrent sessions. A rejected or closed application blocks
re-applying to that opening (W5 PLAN 4.1).

## Visibility

| Who | `job_applications` rows | Opening |
|---|---|---|
| worker | own rows, every status (closed drafts included) | published openings of P15 shops, plus any non-draft opening they hold a SENT application (submitted_at set) to (folded into `jo_select_published_for_workers`) |
| owning owner | SENT rows (`submitted_at is not null`) of openings whose shop they currently own (`is_current_job_opening_owner`: role owner and `shops.owner_id = auth.uid()` via the opening's shop, plus the copied `owner_id`), every later status | own openings (W4) |
| other owners, customers, super_admin | none (no super_admin path until W11) | W4 rules |
| anon | no table privilege | none |

Applicant profiles (`applicant_profiles_for_job_opening`): current owner of the opening's shop
only, for sent rows (`submitted_at is not null`) in submitted, under_review, shortlisted, accepted; sharing ends on rejected, withdrawn and closed;
`display_name` = trimmed `profiles.full_name`, else `Applicant`. Columns: application_id,
display_name, headline, experience_summary, years_of_experience, skills, preferred_locations,
availability_status, availability_notes, profile_updated_at. No contact columns.

### Closed drafts (fix cycle 1, S-B1)

When an opening moves to closed / archived, the auto-close also closes its drafts. They are KEPT
as `status = 'closed'` with `submitted_at` (and snapshot, notice) null, a "closed draft". Chosen
over deleting them because deletion would destroy worker-written text without any worker action,
while a closed draft is unreachable for the owner by construction: the RLS policy, the
applicant-profile window, the certifications RPC, owner transitions and the per-opening cap all
require `submitted_at is not null`, so neither the row nor its cover note ever reaches the owner.
The worker still sees it in their own rows and may delete it (`delete_job_application_draft`).
It sends no notification, does not count as "applied" for opening reads and cannot be sent
(closed is final). Ownership is also checked against the current `shops.owner_id`: if a shop
changes hands (trusted repair only, w2b), the former owner loses every read and action; the new
owner does not inherit earlier applications (copied `owner_id` still required). Owner notifications (submitted, withdrawn, applicant profile removed) go to the current
`shops.owner_id` of the opening's shop and only when it equals the application's `owner_id`;
otherwise none is sent. A transfer repair must realign `job_openings.owner_id` and
`job_applications.owner_id` (trusted session).

## Marketplace search (`search_job_openings`)

SECURITY INVOKER (RLS decides) and only worker accounts get rows; owners, customers and
super_admin get none, anon cannot execute. Published openings of P15 shops with deadline null or
not before today (Manila). Text filters trimmed, <= 80 chars (22023); `%`, `_` and `\` are
escaped. Query matches title, description, work_location, schedule_details; location matches
work_location; skill is a case-insensitive exact element match. Pay uses stated values only:
`p_pay_stated` true = an amount is stated, false = none; `p_pay_period` filters by period;
`p_min_pay_amount` needs `p_pay_period` (22023) and matches `coalesce(max, min) >= amount`; no
conversion between periods, no estimate. `p_limit` 1..50, `p_offset` 0..1000 (22023). Order
`first_published_at desc, id`. `my_application_status` = the caller's non-withdrawn application
status (the row that blocks a new application), else null.

## Audit and notifications (w5e)

See `AUDIT_AND_NOTIFICATIONS.md` (W5 section) for the full catalogue. Summary: one audit event
per create, submit, status change, withdraw, close and delete (subject_type `job_application`,
payload ids and status words plus `changed_by` / `deleted_by`); notifications to the owner on
submit, withdraw and applicant-profile deletion, to the worker on owner decisions, auto-close,
pause and opening removal. Draft edits write nothing. Keys embed the audit event id.

## Limitations

- No auto-close on the deadline (no scheduler): apply refuses instead. Closing updates up to 500 rows in the owner's transaction (R2).
- Snapshots keep owner free text permanently (P20); a W11 takedown can only delete the row through a trusted session (R4).
- Deleting a worker profile removes its applications, accepted ones included; the owner is told without the name (R5).
- Retained application records (W9, `2026_10_26_w9i`, W5-L10): when a shop or owner account deletion cascades and
  deletes an ACCEPTED application while the worker profile still exists, the AFTER DELETE trigger
  `job_applications_retain_accepted` first copies it to `retained_job_application_records` (application id without FK,
  `opening_snapshot`, status, `submitted_at`, `decided_at`, `removed_at`, `removal_reason` = `shop_or_owner_removed`;
  never the cover note). Write-once (no client or trusted update; written only by the trigger), readable by the worker
  only (`my_retained_application_records()`), deleted with the worker profile; audited `job_application_record.retained`.
  Other statuses and worker-side deletions are not retained. Retention periods and erasure rights stay open (W9-L5).
  Accepted applications can also be the D-31 origin of a W9 worker contract (`worker_contracts.job_application_id`,
  `on delete set null`); `accepted` itself is still not a contract (W5-L2).
- Flags rely on PostgREST not exposing `set_config` (smoke `rpc_set_config_not_exposed`, R6). An audit failure aborts the action, cascades included (R9); w5a reduces drift risk.
- The guard message `A submitted application cannot be edited.` is defence in depth: the RPCs never change a non-draft cover note and no client has UPDATE.
- The 500-per-opening cap is tested with 499 trusted fixtures (`j4_w5_opening_application_cap`); the advisory-lock race fix is checked structurally (lock order in the function body, `j17_w5_fix1_closed_drafts_and_current_owner`), not with two concurrent sessions.
- `applicant_verified_certifications` (P22) is real since W7 (`2026_10_26_w7g`, same signature and authorisation): the applicant's CURRENT shop-issued certifications from any shop, never suspended, revoked, expired or superseded rows, reasons or history (W7-L4). The D-20 apply check reads certificate state without a lock (W7 R3); applications sent earlier are never touched by a later suspension or revocation. No contact exchange (D-14), no interview scheduling, no super_admin moderation (W11), no email / SMS / push or Realtime (W12).

## Rollback

Per-file `-- ROLLBACK` blocks in reverse order e, d, c, b, a (local stack only). e: drop the
auto-close, pause-notify and audit triggers and functions (audit rows and notifications stay).
d: drop the three read functions. c: drop the four RPCs, the apply-check helper and the notice
version function. b: restore the W4 `jo_select_published_for_workers` policy, then drop the table
(applications and snapshots lost; export first with a trusted `copy`), the policy helper, the
guard, the normaliser, the snapshot function and `is_current_job_opening_owner`. a: nothing.
